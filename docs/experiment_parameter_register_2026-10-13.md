## 1. 已确认的实验口径

1. 仿真随机生成大量不同结构与特征的应用图、抽象工具和资源条件，不限定四类具体业务。真实应用、工具 API 和任务数据集的设计留到实际场景实验。
2. 不同场景全部从随机权重独立训练。只允许同一场景断点恢复；不采用最大规模训练后续训，不加载教师、蒸馏或旧无效协议权重。
3. 保留模型选择 PPO 训练、冻结模型选择训练部署、共同更新的三阶段框架。每个时隙先部署，后逐 `(应用 a, 接入节点 g)` 模型选择，再解析物理路由与评价。
4. 外生时隙轨迹预先生成，各回合从时隙零重放。分支概率、输入输出 token 代表值在应用生成后固定，跨时隙和回合不变；到达率及允许变化的资源仍可跨时隙变化。
5. 一次生成应用池，固定排列后为不同应用数量选取嵌套子集。不能为每个应用数量重新造图，也不能把未使用工具计入实际工具规模。
6. 只在训练轨迹上评价。最终冻结策略，重放同一条轨迹，不另外生成验证/测试轨迹。不将此结果称为未见场景泛化。
7. 所有节点均允许接入，但部分应用—节点对可以具有零到达率。不固定每应用两个入口，也不强制所有应用在所有节点都有正到达率。
8. 单次推理的输入加输出上限为 **32,768 token**；一次完整应用执行中全部 LLM 请求的累计输入加输出上限为 **128,000 token**。累计预算包含历史上下文在不同 LLM 请求中反复 prefill 的工作量。这两个上限由用户确认，不能写成 JITServe 原文给定的统一上限。
9. 引擎默认值固定到 **vLLM v0.31.0、V1、CUDA 在线服务 `vllm serve`、balanced 模式**。前缀缓存作为明确例外关闭，其余已核对的批处理默认值沿用该版本。
10. Agent 图的轮次、工具扇出、重试次数等数字暂不冻结。先登记生成规则与参考统计，不照搬博士论文的微服务图大小作为 Agent 图上限。

## 2. 七项注释的核查与处理

### 2.1 Energy 的入口到底是什么 :codex-annotation{index="1"}

Energy §3.1 将接入分布定义为 `SD = {λ_s^n : n ∈ N, s ∈ S}`；§4 的观测包含请求由接入服务器转发到首微服务执行服务器的概率。其含义是：用户请求可以在不同边缘服务器接入，接入服务器与首服务的部署服务器可以不同。

需要区分两个“入口”：一条服务链有明确的逻辑首微服务，但这不等于该服务只能从一个固定物理服务器接入。论文没有报告“每服务恰好两个入口”，也没有交代每个 `(s,n)` 的到达率是否全部非零。因此不能把符号的全索引范围解释成全部正到达率的实验事实。[S01]

本研究按用户选择允许零率入口。支持集与入口权重应在场景清单中显式保存；非零入口数量从支持集统计，不再硬设为 2。稀疏支持集的具体抽样分布尚未确定，不假称已由接入日志拟合。若支持集跨时隙固定，零率入口保持为零，避免在训练途中改变动作布局。

### 2.2 Agent 图与微服务图不能直接共用节点范围 :codex-annotation{index="2"}

博士第四章的 12–30 个节点、2–15 层深度描述的是其微服务调用图。Agent 图还包含推理、工具执行、上下文回传、可选继续推理、反思或重试，LLM 请求的工作量会随上下文积累变化。总节点数相同不代表相同推理轮次或工作量。[S02]

因此改为从控制流生成：

- 先形成 LLM 决策/推理阶段及最终响应阶段；阶段之间可直接连接，也可插入工具请求。
- 为工具请求选择串行、并行汇聚或互斥调用关系，不强制 LLM 与工具一对一交替。
- 重试/反思按照有限次展开生成新的阶段，不向 DAG 插入环；不同展开阶段具有不同消息标识。
- 并行分支全部执行，互斥分支只执行选中部分；汇聚之后才能执行依赖这些结果的推理。
- 基础图、工具绑定、概率和 token 抽样决定一个应用配置。图大小、深度、LLM 请求数、工具请求数和 pattern 数由生成结果统计。
- 各个合法 pattern 都要通过两级 token 预算检查。不以总图中所有互斥分支的节点之和代替一次执行的节点集合。

参考证据仅用来说明结构与量级：JITServe 的公开复合样本具有阶段、阶段内请求及 token 字段，存在并行阶段；该样本不代表所有 Agent 图。[S03][S04] 本研究不限定其论文中的四种应用，也不将一个深度研究样本集的阶段数量当作通用上下界。

**用户已经决定：本轮只登记生成规则，生成轮次、扇出、重试等数值不冻结。**

### 2.3 多源资料分别承担不同作用 :codex-annotation{index="3"}

主要长度资料采用 JITServe 公开的 LMSYS 单次请求与深度研究逐次请求记录；其原始背景分别来自真实对话与研究类工作负载。JITServe 的论文提供单次/复合长度与 SLO 的参考，公开数据提供可以直接建立经验分布的字段。[S03][S04]

BurstGPT 保留为通用 LLM 请求长度及到达统计的补充来源，不再作为唯一 token 来源。[S05] Alibaba 与实验室前作提供服务图构建、资源约束和服务处理的参考，而不是 LLM token 分布。[S01][S02][S06]

不把所有数据拼在一起后称为“真实 Agent 分布”。不同来源的 tokenization、单次/累计口径及截断规则必须分别登记；如采用来源混合，混合权重属于本研究的设计选择，尚未冻结。

### 2.4 直接分布采样、历史积累和两级预算 :codex-annotation{index="4"}

撤销“固定 P50/P90/P99 联合分桶后用桶内均值”的默认生成方式。对经过清洗、口径明确的逐次请求建立输入与输出长度的经验边际分布，直接用固定随机种子抽样。每个应用的阶段在生成时抽样一次，保存为代表参数；不会在每个时隙或 PPO 回合重新抽样。

**输入口径必须先辨明。** 数据中的完整 `prompt_len`/`input_tokens` 可能已经包含历史，不能将其作为新增输入后再累加同一段历史。推荐以独立单段 prompt 的长度形成新增指令/外部输入的统计代理；多轮或复合数据的完整输入用于核对累积上下文。若从真实消息序列提取新增内容，须先分离历史，再按固定 tokenizer 计数。将独立 prompt 用作阶段新增输入仍是合成扩展，不能称为原 Agent 轨迹复现。

串行阶段的基本关系是：

\[
P_j = B_j + P_i + O_i + \sum_{h\in\text{本段工具}} D_h,
\]

其中 `B_j` 是新增指令/输入，`D_h` 是实际送入后继 LLM 的工具文本结果，而不是整个文件或二进制回包的字节数。工具可见文本结果的分布目前没有完成提取，列为待确定项，不能自动用“2–10 MB/请求”换成等量上下文。

并行汇聚按导出的消息集合累计：共享历史在**同一次汇聚输入中**只计一次，各执行分支的新输出、可见工具结果及约定保留的消息分别加入。不能直接把两条分支的完整输入长度相加。不同 LLM 请求再次处理相同历史时，那部分输入属于实际 prefill 工作量，仍应计入**应用累计预算**。

对每个合法执行 pattern `s` 检查：

\[
P_{a,i,s}^{m}+O_{a,i}^{m}\le 32768,
\qquad
\sum_{i\in\mathcal V_{a,s}^{\mathrm{LLM}}}
  \bigl(P_{a,i,s}^{m}+O_{a,i}^{m}\bigr)\le 128000.
\]

单次上限还不能超过所选模型/引擎配置实际支持的窗口。超预算处理采用生成时的可行性检查和条件重采样，记录拒绝比例及原因；不在评价时偷偷缩短输出后仍沿用原质量。是否采用显式上下文压缩是独立机制，本轮不加入。

若同一共享节点因上游互斥分支形成不同输入，先逐 pattern 完成上下文和预算检查，再以条件概率计算固定节点代表均值，兼容当前 `P_{a,i}^m` 的节点级建模。不能只检查平均值而让部分执行超过上界。

JITServe 论文的分位数是统计量，不是统一硬上限；公开的请求导出数据也有特定输出截断。用户确认的 32,768/128,000 应单独标为本研究预算。[S03][S04]

### 2.5 工具副本的 CPU 按 Energy 原设定 :codex-annotation{index="5"}

Energy §3.1 明确将每个容器绑定到一个 CPU 核，并在其中部署一个服务实例；CPU 约束为每台服务器所有副本数之和不超过 CPU 容量。主设置因此采用 **每工具副本 1 核**，撤销未经来源支撑的 1/2/4 核分类。[S01]

同类型副本的单位核心服务率按前作保持一致；不根据 GPU 型号推断 CPU 单核速度。不同服务率、主存需求仍可以按前作范围抽样。原文“单位”不能直接当作已经实测得到的请求/秒，时间单位映射必须明确说明。

### 2.6 vLLM 默认值固定版本和入口后核查 :codex-annotation{index="6"}

用户已选择 v0.31.0 的 V1 CUDA 在线服务默认，前缀缓存明确关闭。对于本方案的 RTX 4090/A6000（单卡显存低于 70 GiB），且 `performance_mode=balanced`、不设置批处理覆盖值：

| 配置项 | v0.31.0 在线服务口径 | 与旧建议的区别 |
|---|---|---|
| `max_num_batched_tokens` | 2048 | 不是离线 `LLM(...)` 的 8192 |
| `max_num_seqs` | 256 | 不是配置类测试用 fallback 的 128 |
| `enable_chunked_prefill` | 模型支持时启用；本方案密集模型采用启用 | 保留 chunked prefill |
| 固定 `prefill_chunk_tokens` | 没有固定 512 的上游默认；按剩余 token 预算动态分块 | 删除“512 是 vLLM 默认”的表述 |
| `long_prefill_token_threshold` | 0，不启用独立长 prefill 上限 | 不是固定 chunk 大小 |
| `gpu_memory_utilization` | 0.92 | 不是旧版本/旧配置的 0.9 |
| KV dtype | `auto`，按本方案模型数据类型解析为 BF16 | 记录实际解析值 |
| Prefix caching | 上游支持时默认启用；本方案**显式关闭** | 这是用户认可的实验例外，不冒充默认 |
| Scheduling policy | FCFS；chunked prefill 根据调度预算执行 | 不导入 JITServe 的自定义调度器 |

来源固定为 tag `v0.31.0`，commit `db9527a46873454610df6dbedf79a36d6bf1a7f6`。[S07] 不以会持续变化的 `stable` 页面替代复现版本。双卡显存不能简单相加后套用单卡大于 70 GiB 的默认分支；离线入口、不同显卡或 throughput 模式的默认也不能混用。

当前解析代码仍使用固定 chunk 的工作量关系，**尚未等价实现上述动态分块**。要么按操作点及剩余 token 预算修正解析近似，要么说明采用的近似并校验；不能仅把 512 改成 2048 后宣称完全对齐。本轮只登记这个兼容性任务，不改性能模型。

### 2.7 副本数的上限来自资源，不再硬截为四个 :codex-annotation{index="7"}

Energy 的资源约束没有统一的“每服务每服务器最多四副本”。本方案保留非负整数部署动作，按当前部分部署的资源余量决定动作可行域：

\[
z_{h,n}^{\max}(t)=\min\!\left\{
\left\lfloor\frac{C_{n}^{\mathrm{rem}}(t)}{c_h}\right\rfloor,
\left\lfloor\frac{M_{n}^{\mathrm{rem}}(t)}{m_h}\right\rfloor
\right\},\qquad c_h=1.
\]

其他服务已占用的资源先扣除，之后只允许 `0..z_max`。这仍是有限的离散动作空间，不是“副本无限”。主存需求与 CPU 预算共同限制副本数。[S01]

实现时需去掉现有 `max_tool_replicas_per_server=4` 对部署掩码、部署库、成本参照及动作解码的人工截断。可以按**本场景最大物理可行副本数**设置统一输出宽度，再对每个池应用资源掩码。采用本文不建模的磁盘约束不是必要动作，不能顺手加入新资源维度。
