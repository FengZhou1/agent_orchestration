# Experiment protocol

## Evidence and parameterization

The evaluation follows the same separation used by trace-driven microservice
experiments: production traces determine workload structure and scale, the
simulator evaluates orchestration policies, and controlled benchmark runs
calibrate component performance.

- BurstGPT v2 supplies request timestamps and burst structure. Azure LLM
  Inference Trace 2024 is the frozen external-generalization trace.
- TraceLab v2 and BFCL V3/V4 supply Agent execution patterns, paired LLM-call
  token features, probabilistic pattern flows, and tool-quality tasks.
- Alibaba Microservices v2021 supplies stateless-service graph depth, fan-out,
  reuse, call-rate, and response-time reference distributions. DeathStarBench
  or an equivalent local harness supplies low-load processing time, SCV,
  stable service rate, and serialized payload size.
- Alibaba GPU Trace v2026 supplies joint GPU type/count and CPU-capacity rows.
  It is not used as a request or LLM-latency trace.
- SNDlib supplies the Abilene and GEANT topology and coordinates.
- LLMServingSim 2.0 supplies the full model--GPU performance grid. A small vLLM
  run validates low load, near-capacity load, and long-request-dominant load.

Every processed artifact carries a source checksum, version, license,
preprocessing command, random seed, and split boundaries. Raw public datasets
remain outside the repository.

## Scenarios

| Scenario | Physical graph | Models | Applications | Stateless services | Purpose |
|---|---:|---:|---:|---:|---|
| Toy | 4 nodes | 2 | 2 | 3 | smoke, formula, routing, and exhaustive checks |
| Main | Abilene: 12 nodes/15 links | 3 | 20 | 6 | primary comparison and ablation |
| Scale | GEANT: 22 nodes/36 links | 3 | 50 | 8 | scalability and decision overhead |
| Stress | Abilene/GEANT | 3 | 20/50 | 6/8 | bursts, service slowdown, link loss, GPU unavailability |

The checked-in benchmark scenarios are generated by
`scripts/build_benchmark_scenarios.py`. The three BF16 model tiers are
Qwen2.5-7B, Qwen2.5-14B, and Qwen2.5-32B. Candidate configurations use A10,
L20, and H20 GPUs with fixed vLLM settings: memory utilization 0.9, context
window 32768, batched-token limit 8192, sequence limit 128, chunked prefill
enabled with 512-token chunks, and prefix caching disabled.

The Main scenario contains five templates for each of four families:

1. interactive retrieval: latency-sensitive, one to two LLM stages;
2. transactional tool use: deadline-sensitive;
3. deep research: compound with two parallel service branches;
4. coding Agent: compound with serial and parallel test patterns.

Each family uses short, medium, and long joint input-output token classes. A
class is one application type in the optimization model, so no request-level
optimization variable is introduced.

## Arrival process and splits

- routing slot: 1 second;
- deployment period: 60 slots;
- train/evaluation window: 3,600 slots;
- offered-load levels: 0.40, 0.65, 0.85, and 1.05 of the pinned reference
  deployment's stable capacity;
- chronological split: 60% train, 20% validation, 20% test;
- workflow split: session/task IDs are disjoint across splits.

The primary result replays BurstGPT timestamps after one global time scaling.
The scaling divides every timestamp by the same load factor and therefore
preserves request order, relative burst locations, paired input-output tokens,
and workflow assignments. Two controlled controls use the same request
samples: a minute-level non-homogeneous Poisson process and a homogeneous
Poisson process with the same mean. The legacy 8%/2.5x synthetic burst is only
used by the explicitly named `synthetic-stress` mode.

The balanced workload assigns 25% of offered requests to each family. Four
composition sweeps make one family dominant with shares 60/20/10/10 while
holding total arrival rate fixed. The profile grid also sweeps long-request
fraction and total rate.

## Component parameters

LLM profiles are measured at 20%, 40%, 60%, 80%, 95%, and 105% of stable
capacity for balanced and family-dominant compositions. Required outputs are
TTFT, TBT, complete response time, stable capacity, and KV-token occupancy.
Profiles may omit family fractions only when the backend is deliberately
composition-agnostic.

Six Main-scenario stateless services represent web search, information
retrieval, code execution, file processing, result verification, and an
external API. Scale adds knowledge-graph and data-transformation services.
Profiles cover 1, 2, and 4 vCPU where supported. Arrival SCV and service-time
SCV are retained separately for the GI/G/c approximation. Stable rate is the highest
load with less than 1% errors and P95 latency no greater than twice the
low-load P95. If measurements are unavailable, the initial 2--8 request/s/core
range is reported as a reference range and evaluated at 0.5x, 1x, and 2x.

Application entry and exit payloads use four bytes per token. Intermediate
payloads use serialized request/response bytes from the service profile. A
2--10 MB/request range is reserved for the high-communication sensitivity
case. Network offered load is measured in Mbit/s and is independent of slot
duration. Abilene/GEANT links use approximately 50, 150, or 400 Mbit/s based on
distance; propagation is geographic distance divided by 2e8 m/s, clipped to
1--20 ms. Capacity sensitivity uses 0.5x, 1x, and 2x.

Normalized GPU-hour costs are A10=1, L20=2, and H20=4. Stateless-service cost
is linear in allocated vCPU. All cost coefficients are tested at +/-30%.

## SLO and quality calibration

Before opening the test split, SLO thresholds are frozen from the low-load P95
of a pinned reference deployment:

- latency-sensitive: TTFT=1.5x reference P95 and TBT=1.25x;
- deadline-sensitive: complete response deadline=1.5x;
- compound: each intermediate stage and the entire workflow=1.5x, with final
  TTFT/TBT constraints also applied.

Strict and loose sensitivity settings use 1.25x and 2x. Checked-in threshold
and quality values are marked as reference values and must be replaced by the
pinned calibration output before final paper runs. Quality uses normalized
BFCL, LongBench v2, and SWE-bench Verified scores for the corresponding
application families.

## Comparisons and measurements

Primary policies are Static-Homogeneous, Static-MultiModel, EqualSplit,
LeastLoad, Greedy-SLO, PPO-Deploy, PPO-Route, constrained two-timescale
Joint-PPO, unconstrained Joint-PPO, Joint-PPO+ICM, and Joint-PPO+Potential.
Exhaustive enumeration is limited to Toy.

Every policy reports cost, request-weighted response time, request goodput,
quality, P50/P95/P99 response time, SLO attainment, TTFT/TBT, GPU/KV/service/
link utilization, reconfiguration count, decision latency, and training wall
time. Pilot runs use three seeds, full runs use at least five, and the main
algorithm table uses ten when resources permit. Algorithms share trace windows
and random numbers. Report mean, median, effect size, 95% bootstrap intervals,
and paired bootstrap or Wilcoxon tests with Holm correction.

## Fidelity and acceptance gates

- Hourly request counts, peak-to-mean ratio, and non-zero inter-slot P50/P95
  after preprocessing must differ from the source by no more than 5%.
- Input, output, and total-token P50/P90/P99 must differ by no more than 5%; the
  source request's input-output pair must remain intact.
- Workflow depth, service-call count, parallel width, and pattern-flow
  frequency are checked against their source empirical distributions.
- Stateless-service processing time must come from low-load internal timing;
  production end-to-end RT is not silently substituted.
- On held-out LLM profile points, median absolute percentage error must be at
  most 10% and P95 error at most 20%. Regions outside this gate use the profile
  backend/LLMServingSim replay and are not claimed as analytical predictions.
- Low load must be stable. Near the capacity boundary, waiting and SLO misses
  must increase. Link, service, and long-request stress must affect their
  corresponding utilization and latency metrics.
