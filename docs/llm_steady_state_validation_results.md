# LLM steady-state model validation results

## Scope

This validation compares the current steady-state analytical implementation with LLMServingSim 2.0. The analytical side uses the current model's Roofline service demand, KV-resident capacity, Little-law fixed point, and Allen--Cunneen admission-wait approximation. No simulator output is used to fit those quantities.

The simulator uses the Qwen 3 configurations already defined by the project, one instance, BF16, `max_num_seqs=128`, `max_num_batched_tokens=8192`, 512-token chunked prefill, FCFS continuous batching, and prefix caching disabled. The run script records first-admission waiting, TTFT, TBT, response time, service time, running-request count, and GPU memory reported by the simulator.

## Executed runs

The completed result directory is `results/llm_steady_state_validation_final/`. It combines:

- 4B/A10 and 14B/H20 across interactive, transactional, deep-research, coding, and balanced compositions;
- 8B/H20 and 32B/H20 across interactive and balanced compositions;
- long interactive and transactional windows with 40 requests per load point;
- four offered-load levels, 0.40, 0.70, 0.85, and 0.95 of the analytical capacity;
- one fixed random seed for the completed matrix.

The short mixed-agent runs are retained as composition probes. They are not used as evidence for a final confidence interval.

## Main observations

The simulator's running concurrency and response time increase with offered load for the completed long-window groups. The analytical curves preserve this monotone direction for all completed groups. The TBT comparison is the closest numerical match, with a median group WAPE of approximately 15.6% and a median predicted-to-simulated ratio close to 1.0.

The response and service predictions are conservative. Across the aggregated groups, their median WAPE is approximately 1.43, and the median predicted-to-simulated ratio is about 2.24--2.27. The dominant discrepancy is therefore the Roofline service-demand approximation under continuous batching, rather than the ordering of the load trend.

The analytical waiting term is nearly zero for many groups because the calculated resident capacity is much larger than the fixed-point active concurrency. This agrees with the observed fact that first-admission waiting remains small in the tested finite windows, but it also means that the current model does not explain the simulator's complete response-time increase through queueing. The increase is primarily represented by the concurrency-dependent service-demand term.

The static KV-capacity comparison is in `results/llm_kv_validation/kv_capacity_compare.json`. Using the simulator's GiB memory convention, the calculated capacities differ from the simulator by roughly 2.9%--18.7% in the retained 2-GiB-headroom comparison, while the no-headroom GiB calculation differs by only a few tokens. This validates the per-token KV accounting and identifies the remaining difference as the configured memory-headroom policy.

## Interpretation for the paper

The current equations are suitable as a low-cost, interpretable steady-state surrogate for deployment and routing optimization and for preserving the correct response to load, composition, model size, GPU type, and KV capacity. They should not be presented as a numerically exact replacement for a continuous-batching simulator.

For final evaluation, LLMServingSim replay remains the reference latency backend. The analytical model supplies the optimization-time estimates and the stability/KV-capacity boundary; the simulator supplies request-level TTFT, TBT, and completion-time statistics.

## Reproduction

The validation generator and remote runner are:

```powershell
conda activate agent-orch
python scripts/validate_llm_steady_state_model.py `
  --configs qwen3-4b-a10,qwen3-8b-h20,qwen3-14b-h20,qwen3-32b-h20 `
  --compositions interactive `
  --seeds 0 `
  --requests 40 `
  --min-requests 40 `
  --load-factors 0.40,0.70,0.85,0.95 `
  --workers 2 `
  --output results/llm_steady_state_validation_v3_long_interactive
```

The combined CSV files, trend metrics, figures, and this report are generated by:

```powershell
python scripts/aggregate_llm_steady_state_validation.py
```

## Limitations of the executed matrix

The available remote run was intentionally bounded to avoid a multi-hour deep-research sweep. The completed matrix uses one seed, and the 1.05 overload point was not included in the final run. A paper-grade statistical report should add at least three seeds and longer mixed-agent windows after the analytical approximation is recalibrated or its validity range is explicitly limited.
